# Kojaya Production Bootstrap Manifest

Audit date: 2026-09-26 (Asia/Jakarta). This manifest defines the framework bootstrap only; it is not an instruction to initialize real cooperative business data. RC-03 verification used a newly initialized, isolated PostgreSQL 18 cluster and a synthetic QA administrator. No shared or production database, credential, member record, payment proof, or payment integration was used.

## Database Migration

For a newly provisioned, empty PostgreSQL database, configure the application environment and secrets first, then run:

```bash
php artisan migrate --force
```

RC-03 applied all 182 checked-in migrations to a new PostgreSQL database that initially contained zero public application tables. Do not use a reset/fresh command against an existing database. Confirm the database name and `php artisan migrate:status` before applying forward migrations.

## Organization Bootstrap

Kojaya uses the literal code `KOP-001` as the cooperative head-office anchor in member-numbering, tenant, cooperative registration, and admin-bootstrap flows. That code and its `L0`/`HEAD_OFFICE` role are application identity; alternative production codes are not supported by current source contracts.

The legal/display name and address/contact values are organization-specific, not immutable Kojaya identity. The previous fixed address, phone, and email were examples and have been removed from production seed defaults. On an empty production, staging, or QA database, set `COOPERATIVE_BOOTSTRAP_ORGANIZATION_NAME` to the approved organization name before `db:seed`; optional approved address/phone/email use the corresponding `COOPERATIVE_BOOTSTRAP_ORGANIZATION_*` variables. With no existing KOP-001 and no configured name, `DatabaseSeeder` fails before writing any reference rows. Existing operator-configured KOP-001 records are preserved and are not overwritten by these variables.

Therefore:

- Organization before first login: not inherently required by the authentication schema; login was verified on a fresh install with the seeded anchor, which also supplies the admin organization relationship.
- Organization before cooperative operations: yes; bootstrap creates the anchor, and actual legal identity must be approved before launch.
- Bootstrap source: fixed internal code plus explicit environment-provided name/contact fields; operational child units and branches are configured manually from the real organization structure.

The four contribution types are also created with source defaults, including POKOK/WAJIB suggested amounts. They are policy choices rather than immutable framework values; an owner must review amounts, frequencies, active flags, and POS category applicability before enabling cooperative financial/POS operations.

## First Administrator Procedure

For an empty installation with no administrator import, an authenticated administrator is MANDATORY. After migrations and safe reference seeding, run:

```bash
php artisan admin:create --email=ADMIN_EMAIL --role="System Admin"
```

Use the hidden interactive password prompt, or feed the password from the deployment secret manager through `--password-stdin` in a protected, non-echoing process. Do not place passwords in `--password`, shell history, command-line arguments, CI logs, source, or seeders; `--password` is accepted only in automated testing. The command enforces a valid email and a 12-character password with mixed-case letters, numbers, and symbols, hashes it, marks a new administrator email verified, and assigns the selected allowlisted role. A new user receives `organization_id` for KOP-001 when that anchor exists. Duplicate email creation is rejected unless `--update-existing` is explicitly supplied; updates preserve the password unless a new one is explicitly provided.

If real users are imported, verify at least one active administrator, correct role mapping, organization relationship, and verification policy instead; do not create an extra admin merely to satisfy the checklist. The command does not print the password.

## Idempotency and Verification Evidence

The production-safe bootstrap was replayed twice against the same isolated, newly initialized PostgreSQL 18 database. Counts and semantic row fingerprints (excluding timestamps) were identical for roles, permissions, role mappings, organization, contribution types, POS categories, loan types, tax rules, job grades, leave types, salary component types, and shifts. The expected single TaxRule `updateOrCreate` rule remains an intentional source-of-truth update; role mappings likewise reconcile to `RolePermissionSeeder` source policy. Other safe reference records use unique business keys and `firstOrCreate` and preserve operator-managed values.

First safe seed observed: 182 migrations; 16 roles; 129 permissions; 476 mappings; 1 organization; 4 contribution types; 6 POS categories; 3 loan types; 1 tax rule; 6 job grades; 6 leave types; 5 salary component types; 4 work shifts. Users, members, employees, departments, POS products/transactions, cooperative payments, and ledger entries were all zero immediately after the safe seed. A synthetic QA admin was then created with `admin:create`, linked to KOP-001 and System Admin, authenticated over HTTP, loaded the protected dashboard (200), logged out, and was redirected to `/login` on the next dashboard request.
