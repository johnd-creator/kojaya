# v0.1.0 Release Readiness

## Release classification

- Internal Alpha
- Cooperative Backend Baseline
- Not Production Release

The application release `v0.1.0` was tagged and published as an internal-alpha
GitHub pre-release. The API contract remains version `1.0.0`; it is not the
application release version.

## Included scope

- Document 01 P0 security and correctness remediation.
- Document 02 payment and reservation state-machine remediation.
- Document 03 PII encryption foundation and staged rollout controls.
- Document 04 organization authorization and token metadata remediation.
- Document 05 audit, pagination, and API contract remediation.
- PostgreSQL concurrency enforcement in CI.

These entries describe the internal-alpha baseline and do not claim that all
Legacy ERP behavior is production-ready.

## Known limitations

- 42 Legacy ERP test files remain excluded from the default PHPUnit suite.
- Approximately 161 Legacy ERP test methods are not part of the default release gate.
- Five pre-existing skipped tests remain unchanged.
- Midtrans is not production-active for this baseline.
- WhatsApp and FCM still require credentials and live validation.
- PII rollout remains staged/dual-write; plaintext retirement and backfill are not
  completed release claims.
- Granular token cutover remains in the instrument phase.
- Production deployment, backup rehearsal, PII backfill, and live webhook validation
  are not part of this baseline.
- Composer critical/high/unknown advisories are cleared by the approved stable
  resolution. One moderate and three low advisories remain and are recorded below
  as residual risk; they are not hidden by package-wide ignores.
- NPM production audit after the scoped lockfile remediation reports 0 critical,
  0 high, 1 moderate, and 1 low advisory.

## Excel usage inventory

- The application has both export and import usage.
- Exports include member XLSX files, payroll/attendance/leave/compliance XLSX
  reports, and a reusable `Excel::download` service.
- Budget line import accepts user-uploaded XLSX/CSV files and uses
  `Maatwebsite\Excel` validation/model import. This is untrusted input at the
  application boundary.
- Member export uses `Excel::store` and `Excel::raw`; tests load generated XLSX
  output through `PhpSpreadsheet\IOFactory`.
- `StoreCooperativeMemberRequest` uses PhpSpreadsheet's Excel serial-date helper,
  so PhpSpreadsheet is not export-only.
- No `WithMultipleSheets`, HTML reader, or queued Laravel Excel export was found.
  The unrelated PDF report job is queued, but the spreadsheet exports are request
  driven.
- Integration protection exists in the member export authorization tests and the
  budget import feature test; the default Legacy ERP quarantine affects the budget
  import test's release-gate status.

## Tag and branch policy

Tag `v0.1.0` is created and immutable at `ad8bc3afc9b62f549e4f054e181ef9decbecb341`,
the exact green main commit from PR #10. The tag must not be moved or deleted
after creation.

Recommended main protection for senior approval:

- Require a pull request before merging and restrict direct pushes to `main`.
- Require: Pint, Frontend Build, Generated Drift, PHPUnit Parallel, Migration and
  Seed, OpenAPI Drift, PostgreSQL Concurrency, and Dependency Audit.
- Require the branch to be up to date where compatible with the team workflow.
- Block force pushes and branch deletion.
- Protect `v*` tags with a tag rule/ruleset.
- Dependency Audit is now a required candidate check; it has no bypass,
  `continue-on-error`, or hidden high/critical/unknown advisory.

## Deployment safety correction

- The workflow requires an explicit deployment ref, checks out that ref on the
  GitHub runner, and resolves it once to a complete 40-character commit SHA.
- The exact SHA is passed to the remote command; the runner's checked-out
  `bin/deploy.sh` is streamed through SSH, so the server's existing deploy script
  is not trusted as the bootstrap entry point.
- The remote script fetches and verifies the exact commit, enables maintenance
  mode using the current application, then checks out the target SHA and refreshes
  Composer, Laravel, and frontend artifacts before migrations and cache rebuild.
- If a post-maintenance step fails, the application remains in maintenance mode.
  The script reports the target and previous revision for diagnostics and requires
  manual inspection or rollback; it does not attempt an incomplete automatic
  rollback or automatically bring the application up.
